# Phase 4 Stack — Concurrency Architect Review

**Verdict: BLOCKING** — one finding will silently waste every async cold-load in production.

## Findings

### HIGH (BLOCKING) — coldLoadStoppedMember missing inst.state flip
**File:** `internal/jukebox/sleep.go` (coldLoadStoppedMember success branch, ~line 474-489)

After async `KickColdLoad` completes a successful cold-load, `coldLoadStoppedMember` calls `s.admission.NotifyStarted(inst.model)` (flipping admission to `admissionSleeping`) but **never flips `inst.state` to `StateSleeping`** in the scheduler's instance map. The scheduler still sees `StateStopped`.

**Triggering scenario**: Next consumer request → `AcquireRoute` → `tryRouteReady` (fails, state=`StateStopped`) → `tryRouteFromSleep` (fails, checks `inst.state != StateSleeping`) → full scheduling path → `evictConflicts` sees stopped instance on target GPUs → `drainAndStopInstance` deletes it from the map → fresh instance creation from scratch. Admission books now have stale L1 residual for a model whose instance was just discarded = double-accounting bug.

**Evidence the bug exists**: `integration_stop_test.go:226-229` explicitly works around it by manually mutating `inst.state` in the test body (this is suspicious test code that was flagged by the test-design reviewer independently).

**Fix**: In `coldLoadStoppedMember` after the `NotifyStarted` call, add:
```go
s.mu.Lock()
inst.state = StateSleeping
s.mu.Unlock()
```
`RedeployMember` at `redeploy.go:429-431` already does this correctly; `coldLoadStoppedMember` is the only caller that doesn't.

### MEDIUM — peerInst.state read without s.mu in RedeployMember step (a2)
**File:** `internal/jukebox/redeploy.go:273`

`peerInst` obtained under `s.mu.RLock()` (lines 266-268), but `s.mu` released before the `== StateStopped` check at line 273. A concurrent idle-suspend or admission-eviction goroutine can write `inst.state = StateStopping` between RUnlock and the check, causing `RedeployMember` to double-stop a peer mid-stop.

**Fix**: Re-acquire `s.mu.RLock()` for the state check, or widen the original scope. Pattern already established at `tryRouteReady` lines 372-378 (double-check under lock).
