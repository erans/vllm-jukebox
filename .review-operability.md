# Phase 4 Stack — Operability Architect Review

**Verdict: needs polish** — core mechanics sound. 3 HIGHs that will generate 3am tickets.

## HIGH findings

### #1 — StateStopped invisible to /health accepting_requests
**File:** `internal/httpserver/handlers_health.go:22-23`

`/health` only promotes `StateSleeping` to `accepting_requests: true`. If ALL ready instances are Stopped (host reboot, full cold deploy), `/health` returns `accepting_requests: false`. Upstream LB drains traffic from a jukebox that's actually serving via async-503+KickColdLoad. The drain cuts off the recovery loop.

**Fix**: Add `StateStopped` to the accepting promotion alongside `StateSleeping`. A Stopped model is warm-on-demand just like Sleeping — both surfaces should signal "accepting (with latency)".

### #2 — KickColdLoad lock-wait has no operator visibility
**File:** `internal/jukebox/sleep.go` (KickColdLoad goroutine)

If N swap-group peers all arrive Stopped simultaneously, N goroutines stack on coldLoadMu. The Nth goroutine's 10-min ctx can expire while still waiting. No operator-visible signal: no log line on lock-wait-entry, no metric, no status field showing "N queued behind cold-load lock". 3am operator sees KickColdLoad kicked but nothing for 10 minutes — can't distinguish "cold-loading slowly" from "stuck".

**Fix**: `slog.Info("cold_load_queued_behind_lock", "model", name)` before WithColdLoadLock + `slog.Info("cold_load_acquired_lock", "model", name)` at top of callback. Emit `jukebox_cold_load_queue_depth` gauge.

### #3 — Redeploy peer-stop failure leaves VRAM accounting wrong
**File:** `internal/jukebox/redeploy.go:297-301`

When peer `docker stop` fails, code logs WARN and continues. Admission has already booked the peer as Stopped (zero VRAM), but if docker stop failed because daemon was transiently unreachable, the container may still be running and consuming GPU memory. Target cold-load may then OOM with no actionable error tying it back to the peer-stop failure.

**Fix**: Emit `slog.Error` not `slog.Warn` for peer-stop failure. Emit `LogLifecycleTransition` with reason `"stop-failed-vram-drift-risk"`. Consider 207 Multi-Status with `peer_stop_failures` in the JSON body.

## MEDIUM findings

- `/status` `accepting_requests: false` when all instances Stopped → false-alarm potential during routine redeploy-member.
- `bestEffortRestorePinned` partial-state contract not documented — operator sees 500, may miss the `left_stopped` field inside `result`.
- Boot-probe log line doesn't include sleep_mode status — confusing when both `evict_action: stop` and `sleep_mode: false`.
- `/admin/redeploy-member` admin endpoint has no auth — protection is an undocumented compose binding contract. Misconfiguration exposes a 5-minute-blocking RCE-equivalent.

## LOW findings

- `pollUntilSleeping` (redeploy.go:396-420) treats ANY non-error as success — doesn't check `is_sleeping=true` like `doColdLoad` correctly does. Race window where vLLM HTTP is up but model not loaded.
- `KickColdLoad` 10-min ctx + 5s poll on dead docker.sock = 120 retry errors per failure window.
- Auto-restore wake emits `instance_woken` but not `lifecycle_transition` — breaks `grep lifecycle_transition` operator runbook.

## Best operator-facing message
`admission_evicting` (admission.go) — model + victims + needed_mb_per_gpu + gpus in one line. Causality, magnitude, affected resources.

## Worst operator-facing message
`"pause pinned peer \"vllm-main\": sleep API: POST /sleep: context deadline exceeded"` — tells operator nothing actionable. Network? vLLM hung? Retry now or wait? Pinned peer wedged sleeping or still awake?

## Deployment skew: restart:unless-stopped
If `docker stop` succeeds and daemon auto-restarts a container, jukebox has already called `NotifyStopped` but container is back serving. **Net effect: self-heals** — next consumer request hits 503+Retry-After+KickColdLoad → `docker start` on already-running container exits 0 → `/is_sleeping` returns immediately → NotifyStarted. Cost: one wasted 60s window per consumer request that arrived during the gap, plus confusing 2-3 second "cold-load" log lines.

## Retry-After:60 vs ~5min cold-load mismatch
Clients with max-retry 3-5 give up at 3-5min, before cold-load completes, surfacing errors to humans. Hard-coded `"60"` doesn't distinguish "sleeping (30s wake)" from "stopped (5-8min cold-load)". **Fix**: use `IsModelColdLoading` to set Retry-After to 300 for cold-loads, 60 for sleeping.
